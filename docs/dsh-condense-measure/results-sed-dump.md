# `sed` 大窗口与原始转储：三个数与硬判据（票 14 / task-3）

计划 §4.4 第 2、3 行两个命令族 handler 的测量读数。语料 `/tmp/dsh-condense`
（106,504 次 `bash`+`pwsh`，2026-10-16 抽取；其中 41,523 次低于尺寸下限、不进读数）。
读数全部来自 `harness.py` 的 `measure_dispatch` 真跑，`triggered` 口径的分母只有真正被替换的调用。

## 结论

**默认跑的就是 §4.4 那张有序规则表**（sed 大窗口 → cat → ls → head → tail → nl，首个命中者胜）：

| 运行 | targeted | triggered | 守卫放弃 | 省幅 `all` | **省幅 `triggered`** |
| --- | ---: | ---: | ---: | ---: | ---: |
| 有序规则表（两张 handler 合跑） | 64,976 | **3,878** | 7,879 | 8.0% | **68.8%** |
| 拆开：② `sed` 大窗口（≥101 行） | 64,976 | **1,331** | 197 | 3.1% | **69.0%** |
| 拆开：③ 原始转储 `cat`/`ls`/`head`/`tail`/`nl` | 64,976 | **2,547** | 7,682 | 4.9% | **68.7%** |

合跑的 `triggered`（3,878）= 两张拆开之和，`triggered` 省幅的分母
6,756,392 = 2,591,792 + 4,164,600 也逐位相等——**首命中者胜生效，没有一行被两条规则重复
吃掉或漏掉**，两张 handler 的读数可以分开引用。

| handler | 参数 | **达到 / 未达到 60%** |
| --- | --- | --- |
| ② `sed` 大窗口（≥101 行） | 头 20 / 尾 20 / 守卫 60 行 | **达到（69.0%）→ 发布** |
| ③ 原始转储 | 头 15 / 尾 15 / 命中行 ≤20 / 守卫 60 行 | **达到（68.7%）→ 发布** |

两个 handler 都过线，且**余量不是靠缩放口径得来的**：分母由 harness 打印（见复现命令）。
第三个数字（守卫放弃）的含义是「结果根本不是大窗口/大转储」——文件比请求的窗口短、或输出
被下游 `| head` 截掉了，所以按 §4.1 的忠实性守卫弃权，不算失败。

**两个 handler 的省幅都来自「头尾各留十几行、丢掉中段」**（§4.1 第 3 条的有损压缩），
不是砍语义上下文；落地时必须带回退入口，harness 的 `fallback_notice` 已计入上面的节省额。

## 复现

```
cd docs/dsh-condense-measure
python3 transforms_sed_dump.py                      # 默认：整张有序规则表（约 20 秒）
python3 transforms_sed_dump.py --only sed           # 拆开只跑 ②
python3 transforms_sed_dump.py --only dump          # 拆开只跑 ③（5 条命令名规则）
python3 transforms_sed_dump.py --recon              # 脚手架剥离覆盖（纯计数，15 秒）
```

敏感性各行用同一模块的开关复现：`--only sed --head 30 --tail 30`、
`--only sed --head 50 --tail 200`、`--only sed --min-lines 101`、
`--only dump --head 30 --tail 30`、`--only dump --hits 0`、`--only dump --min-lines 101`。

## 分派：脚手架剥离前后各覆盖多少条调用

`--recon` 的读数（106,504 次 `bash`+`pwsh`）：以 `echo` 为整条命令第一个 token 的
1,096 次；含**以 `echo` 打头的链段**的 45,248 次；含 `&&` 84,939、`|` 70,613、
`;` 51,133、`||` 3,850 次。

| 家族 | 不剥脚手架（整条命令第一个 token） | 剥脚手架 + 拆链后 | 覆盖 |
| --- | ---: | ---: | ---: |
| ② `sed` 大窗口（≥101 行） | 333 | **1,620** | ×4.86 |
| ③ 原始转储 | 4,327 | **16,670** | ×3.85 |

**不剥脚手架，`sed` 大窗口会漏掉 79% 的命中**（1,620 里只看得到 333），原始转储漏 74%。
剥离做法就一条：按 `&&` / `||` / `|` / `;` / 换行拆段（**引号内的分隔符不算**，否则
`grep -E 'a|b'` 会被拆坏），跳过 `cd`/`echo`/`printf`/`set`/`export`/`source`/`.`/`true`/
`:`/`pwd`/`pushd`/`popd`/`ulimit`/`umask` 与赋值语句，取第一段。

一处与任务书不符、按实测报：任务书写的「5,334 次 `echo` 打头、其中 5,278 次是
`cd X && echo "标题" && 真命令` 形状」在本语料上**复现不出来**——`echo` 真是第一个 token
的只有 1,096 次；宽松的 `^cd … && echo` 是 6,285 次、严格的
`^cd X && echo … && 真命令` 是 4,399 次。结论方向不变（不剥离会大面积漏），但基数以实测为准，
不要引用 5,334。

## 参数选择与敏感性（全部真跑）

保留预算就是这条 handler 的「策略」。两个家族的守卫下限都取 60 行——低于它就是
glance 尺寸，不值得冒险；单行截断 2000 字符与 §4.5 的封顶参数一致。

| 变体 | triggered | 省幅 `triggered` | ≥60% |
| --- | ---: | ---: | --- |
| ② 头 20 / 尾 20，守卫 60（**默认**） | 1,331 | 69.0% | ✅ |
| ② 头 20 / 尾 20，守卫 101（计划字面的「大窗口」） | 1,234 | 70.2% | ✅ |
| ② 头 30 / 尾 30，守卫 60 | 1,322 | 54.9% | ❌ |
| ② 头 50 / 尾 200（§4.5 的**通用封顶**参数），守卫 60 | 42 | 28.1% | ❌ |
| ③ 头 15 / 尾 15 / 命中 ≤20，守卫 60（**默认**） | 2,547 | 68.7% | ✅ |
| ③ 头 15 / 尾 15 / 命中 0，守卫 60 | 2,547 | 72.7% | ✅ |
| ③ 头 15 / 尾 15 / 命中 ≤20，守卫 101 | 988 | 78.8% | ✅ |
| ③ 头 30 / 尾 30 / 命中 ≤20，守卫 60 | 2,236 | 48.3% | ❌ |

两条读数值得写进设计文档：

1. **§4.5 的通用封顶参数（50/200）在 `sed` 大窗口上只有 28.1%**——只有 42 次触发。
   `sed` 窗口的中位数才 110 行，通用封顶的 300 行总额度几乎从不生效。所以 §4.4 第 2 行
   「策略依赖」的答案是：**必须用比通用封顶紧得多的窗口专用预算**，20+20 行是实测过的
   最松的可过线档（30+30 就掉到 54.9%）。
2. 转储族把保留量抬到 30+30 就掉到 48.3%，所以 15+15 也不是随手取的。

## 已知边界

1. **守卫用的是「结果行数」，不是 `stdout.truncated`。** 语料里 `bash` 结果的 `meta`
   只有 `cwd`，工具自身的截断事实拿不到（README「已知边界」第 3 条），所以「输入已被
   截断就不输出跨文件聚合量」这条守卫在离线测量里只能以行数下限近似；运行期该 fact 可采。
2. **包装命令没有解包装。** `timeout 30 cat …` / `time cat …` 这类按未命中处理。实测
   这类只在转储族多 5 次调用（**0.03%**）、`sed` 上 0 次，收益低于维护成本，故未实现。
3. **首个实质命令是 `sed`/`cat` 但结果来自下游的调用会落进本族**（如 `cat f | grep x`）。
   行数守卫挡掉了其中的小结果，规模影响未单独量化。
4. **`sed` 窗口只认 `-n` 的打印区间**（`sed -n '100,400p'`，含 `$` 与多区间求和）；
   `sed 's/x/y/'`、`sed '5,10d'` 这类不是窗口，正确地不匹配。
5. **harness 的两处缺陷（`triggered` 分母、多规则分派的错误断言）由 lead 在测量期间修好**，
   本模块没有改 `harness.py`、也没有留旧公式的副本；上面每个数都是修好后的
   `measure_dispatch` 直接打出的。修复前的手工补算与修复后的读数逐位相同
   （69.0% / 68.7%），互为交叉验证。

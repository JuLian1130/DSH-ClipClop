# sed 与 grep：用途与上下文成本

《[DSH bash 使用情况调研](dsh-bash-usage-report.md)》的续篇，回答四个问题：

1. `sed -n 'a,bp'` 与 `grep -n -A -B -o` 在 DSH 轨迹里各自是干什么用的？
2. 平均 1,087 / 698 token 一次，是真的需要这么多信息吗？
3. 哪些高频场景可以把进入上下文的 token 压下来（精简结果，或合并串行的多步输出）？
4. 哪些看着可疑、其实不值得动的场景？

**结论速览**

| 问题 | 答案 |
|---|---|
| sed 是干什么的 | **精确读取器**：读一段已知位置的内容。85.8% 的出现是 `-n 'a,bp'`，读代码 64%、读文档/票据 21%；窗口中位 **36 行**。93.5% 的目标文件本会话根本没改过 → 主要用途是**理解与参考**（含跨仓阅读），不是"读后即改"。 |
| grep 是干什么的 | **定位与筛选**：一半以上 pattern 是带 `\|` 的多别名正则；**27.7% 的 grep 调用下一步就用 sed 读同一文件**；12.4% 的出现是 `-v` 反选过滤（多在管道里，不产信息）；6.5% 是存在性/计数。 |
| 平均 token 需要吗 | **中位数需要，均值不需要**。一次调用平均含 1.70 个 grep / 1.48 个 sed，拆到单个命令是 **410 / 736 token**；中位调用只有 342 / 716 token（≈ 读一个函数的最小量）。均值被长尾拉高：grep 最大 10% 的调用占 **48.3%** 的 grep token，sed 占 **38.6%**。 |
| 能省多少 | 两个有实证支持的高频口子（定位型 grep 的命中列表、大上下文 grep）合计可省约 **1.4M token**（≈ sed+grep token 的 8%，全部 bash token 的 3.8%）。整段文档式 sed 是更大的口子，但"省多少"取决于策略而非重复投递。 |

## 口径

| 项 | 值 |
|---|---|
| 基准快照 | 同报告：[`bash-calls-classification.csv`](dsh-bash-usage/bash-calls-classification.csv)，去重后 **44,216 次 bash 调用**（冻结快照） |
| 命令出现次数 | 解析调用内每个顶层简单命令：grep **32,050** 次、sed **15,236** 次（与 [`direction.py`](dsh-bash-usage/direction.py) 的 32,069 / 15,242 差 <0.1%，口径一致） |
| token 归属 | 沿用报告口径：一条调用的结果 token 记给**首个实质命令**。因此「调用级」表里的 token 只统计该命令为首位实质命令的调用 |
| 「出现级」vs「调用级」 | 调用级：grep 12,416 次调用 / 8,671,381 token，sed 7,273 次 / 7,905,506 token，合计占全部 bash token 的 **45.4%**。出现级：一条调用里可能有多条 grep/sed，只数命令个数。解析器要求命令以 `grep`/`sed` 开头，`{ grep … }`、`( grep … )` 这类分组写法会被漏掉：grep 少 3 条（12,413 / 12,416），sed 无漏 |
| 中间数据 | `OUT_DIR/sedgrep_parsed.jsonl`（27,267 条含 sed/grep 的调用，带解析后的形状、窗口、目标文件、原始结果文本） |
| 附带数据 | `OUT_DIR/all_tools.jsonl`（全工具调用，用于判断"这一步之后改没改这个文件"） |

## 一、sed 在做什么

### 形状：85.8% 是打印行区间

（报告里"96.6% 是 `-n 'a,bp'`"只数"读"的分母；这里 85.8% 的分母是全部 sed 出现，含 `-i` 与重定向写。）

| sed 形式 | 出现 | 占比 | token（作首位实质命令的调用） |
|---|---:|---:|---:|
| `-n 'a,bp'` 打印行区间 | 13,067 | 85.8% | 7,293,673 |
| 其他 stdout 形式 | 921 | 6.0% | 370,787 |
| `-n 'Np'` 单行 | 779 | 5.1% | 139,830 |
| `/re/p` 正则打印 | 302 | 2.0% | 83,853 |
| `-i` 原地写 | 134 | 0.9% | 15,091 |
| 重定向写 | 30 | 0.2% | 1,233 |
| `s///` 替换 | 2 | 0.0% | 19 |

### 窗口：中位 36 行，90 分位 101 行

| 窗口（行） | 次数 | 占比 | token | token 占比 |
|---|---:|---:|---:|---:|
| 1–10 | 1,302 | 10.0% | 247,645 | 3.4% |
| 11–20 | 2,473 | 18.9% | 727,399 | 9.8% |
| 21–40 | 3,496 | 26.8% | 1,587,324 | 21.5% |
| 41–60 | 2,491 | 19.1% | 1,575,548 | 21.3% |
| 61–100 | 1,988 | 15.2% | 1,529,614 | 20.7% |
| 101–200 | 1,143 | 8.7% | 1,406,958 | 19.0% |
| 201–500 | 166 | 1.3% | 300,632 | 4.1% |
| 501+ | 7 | 0.1% | 15,678 | 0.2% |

中位 36 行、p25 17、p75 61、p90 101、p99 231、max 771。行宽中位 44 字符 / **11.2 token**，所以中位窗口 ≈ 400 token。
89.6% 的调用拿到的是完整请求窗口（其余 10.4% 是文件比窗口短，请求落空）。

### 目标：代码 64%、文档 21%

| 目标类型 | 次数 | 占比 | 平均 token/次 |
|---|---:|---:|---:|
| 源码（.ts 7,603 / .py 414 / .js 295 …） | 8,543 | 65.4% | 452 |
| 文档（.md 2,533） | 1,780 | 13.6% | 1,021 |
| 无扩展名（临时/探针文件为主） | 1,418 | 10.9% | 49 |
| 票据（`.scratch/issues/*.md`） | 900 | 6.9% | **1,631** |
| 配置 | 394 | 3.0% | 296 |

### 读完之后的动作

| 之后的动作 | 次数 | 占比 | token |
|---|---:|---:|---:|
| 本会话再没读/写同一个文件 | 4,319 | 64.7% | 4,956,660 |
| 此前 3 次调用内有 grep 定位同文件 | 1,863 | 27.9% | 1,982,505 |
| 本会话稍后改同一文件 | 216 | 3.2% | 213,891 |
| 本会话 read 工具又读同一文件 | 141 | 2.1% | 142,190 |
| 8 次调用内就改同一文件 | 135 | 2.0% | 95,876 |

按**是否被本会话编辑过**看（6,674 次可解析路径的 sed 读）：改前查阅 2.9%、改后读回验证 3.6%、**本会话从未改过该文件 93.5%**（其中代码 4,352、文档 814、票据 538、临时/探针 265）。

> 换句话说：这里的 sed 不是编辑器，也不主要是"改文件前先看看"。它是**定位之后的精读器**（28% 的读前面紧跟着一次 grep）＋**改完之后的验证器**（3.6%）＋**跨仓/跨文件的参考阅读器**（多数）。读回验证这一类完全可以被 `read` 工具的 offset/limit 替代。

## 二、grep 在做什么

### 形状：78.7% 内容检索，12.4% 是管道过滤

| 形状 | 出现 | 占比 |
|---|---:|---:|
| 内容检索（`-n` / `-A` / `-B` / `-o` …） | 25,233 | 78.7% |
| `-v` 反选（几乎都在管道里） | 3,965 | 12.4% |
| 存在性 / 列文件名（`-l`） | 1,128 | 3.5% |
| 计数（`-c`） | 945 | 2.9% |
| `-o` 只取匹配片段 | 756 | 2.4% |
| `-q` 静默 | 23 | 0.1% |

### 常用 flag 组合（内容检索）

| 组合 | 次数 | 平均 token/次（作首位实质命令的调用） |
|---|---:|---:|
| `-n` | 9,834 | 392 |
| `-n -r` | 6,533 | 264 |
| `--include -n -r` | 2,417 | 445 |
| `-A -n` | 1,555 | 526 |
| `-A -B -n` | 372 | 533 |
| `-E`（多别名正则，配 `\|`） | 1,354 | 3 |
| `-o` | 550 | 36 |

### 检索范围

| 范围 | 出现 | 占比 |
|---|---:|---:|
| 单个/若干具名文件 | 12,741 | 39.8% |
| 递归目录（`-r`） | 11,147 | 34.8% |
| 管道 stdin（纯过滤，无文件参数） | 7,477 | 23.3% |
| glob / 目录通配 | 682 | 2.1% |

### pattern 类型

| 类型 | 出现 | 占比 | 平均 token/次 |
|---|---:|---:|---:|
| 正则 / 多别名（含 `\|`） | 12,888 | 49.6% | 361 |
| 单个标识符 / 单词 | 6,636 | 25.5% | 251 |
| 复合表达式 | 5,345 | 20.6% | 225 |
| 中文短语 | 1,115 | 4.3% | **798** |

### 之后发生了什么（grep 作首位实质命令的 12,413 次调用）

| 之后 | 次数 | 占比 | token |
|---|---:|---:|---:|
| 4 次调用内没有同文件的 sed/edit/read | 8,165 | 65.8% | 5,844,248 |
| **grep 定位 → 随后 sed 读同一文件** | 3,441 | 27.7% | 2,335,035 |
| grep → read 工具读同文件 | 640 | 5.2% | 395,732 |
| grep → 直接编辑同文件 | 165 | 1.3% | 95,218 |

另外，在 grep 作首位实质命令的调用里，**62.2% 的下一个顶层命令就是 `head`**（7,716 次，5,065,804 token）——grep 的输出基本已经被 `head` 收过一次口。

## 三、698 / 1,087 token 是真需要吗

**先拆平均**：一条调用里平均有 **1.70 个 grep**（12,413 次调用 / 21,132 次出现）、**1.48 个 sed**（7,273 / 10,739）。所以 698 / 1,087 不是"一次检索"的价格，拆到单个命令是 **410 / 736 token**。

| | grep（首位实质命令） | sed（首位实质命令） |
|---|---:|---:|
| 调用数 / token | 12,413 / 8,670,351 | 7,273 / 7,905,506 |
| 平均 / 中位 | 698 / **342** | 1,087 / **716** |
| p90 / p99 / max | 1,519 / 5,605 / 33,664 | 2,141 / 6,990 / 15,869 |
| >2,000 token 的调用 | 852 次，占 40.6% token | 824 次，占 41.2% token |
| 最大 10% 调用占 token | **48.3%** | **38.6%** |
| 一半调用（中位以下）占 token | 10.1% | 18.5% |

**判断**：

- **中位调用是需要的。** sed 中位 = 36 行 × 11.2 token ≈ 400 token，这就是"读一个函数体"的下限；grep 中位 342 token 是"一处命中的若干上下文"。`-o` 一类廉价用法（平均 36 token）已经很省。
- **均值不代表典型。** 平均值被长尾拉高：grep 一半的 token 集中在最大 10% 的调用里（sed 是 39%）。真正的开销是少数大扫描与大文档读：

  ```
  33,664 | grep -rnwiE "stored|stores|storage|retain|…|persisted" . | grep -v … | head
  30,848 | grep -rn "eventSource" packages/client/ui-chat/src/client/*.ts | head -20; …
  15,509 | sed -n '1,200p' .scratch/historical-reasoning-pruning/issues/07-gate-bd-experiment.md
  14,887 | sed -n '1,120p' .scratch/historical-reasoning-pruning/issues/07*.md | head -150
  ```

- **长尾里有明确可削的部分**，见下节。

## 四、可精简的高频场景

按"证据强度"排序：重复投递是**可证的浪费**（同样的内容在多次结果里出现），策略性截断是**需要决策**的取舍。

| # | 场景 | 频次 | 可省估计 | 证据强度 | 做法 |
|---|---|---:|---:|---|---|
| 1 | **定位型 grep 的命中列表**：grep 之后 1–3 次调用内用 sed 读同文件 | 1,724–3,441 次链，grep 侧 1.2M–2.3M token（1,724 是能解析出命中行的链，3,441 是所有"grep 后 4 次内 sed 读同文件"） | **≈ 0.72M**（截到前 8 条命中：从平均 19.6 条带行号行里省 53.2%） | 强（链 + 行数分布实测） | 定位步骤只回"前 N 条命中 + 共 M 处"；需要上下文时让下一步一次读够 |
| 2 | **大上下文 grep**：`-A/-B/-C`，输出里 91.1% 是上下文行（34,371 / 37,745） | 973 次调用 / 1.04M token | **≈ 0.67M**（上下文封顶 3 行/命中，影响 830/973 次调用） | 中（不是纯浪费，是策略） | 上下文按需给：命中少时给足，命中多时封顶 |
| 3 | **整段文档/大窗口 sed**：窗口 ≥101 行 | 1,316 次出现 / 1.72M token（23.6% 的 sed token）；票据类平均 1,631 token/次 | 取决于策略（按标题取用可省一半量级） | 假设依赖 | 按小节/标题给，或先给结构再按需展开 |
| 4 | 同会话重复读同一行区间 | 2,176 个"被读 ≥2 次"的 (会话,文件)，重复行只占 **5.2%** | ≈ 0.05M | **否证**：太小 | 不值得为它加机制 |
| 5 | 管道过滤 grep（`\| grep -v`，7,477 次出现）与 `\| head` 收口（7,716 次调用） | — | 0（已省） | 已最优 | 不动 |

第 1、2 项合计约 **1.4M token**，占 sed+grep token 的 8.4%、全部 bash token（36.5M）的 3.8%。第 3 项是更大的口子，但不能算作重复投递。

**串行的两条路，代价不同**：

- grep → sed 这条两步链（3,441 次，占 grep 调用的 27.7%）**不该简单合并**：把 sed 的窗口并进 grep 就得给每个命中都带一次上下文，输出反而更大。真正省 token 的是**砍掉定位步骤里用不上的命中行**（85.5% 的带行号行不落在随后 sed 的窗口里），保留"有几处、大致在哪"。
- sed 连读同一文件（1.48 个/次调用，把相邻窗口放进同一条调用）已经在做，重复率只有 5.2%，没有进一步合并空间。

## 五、可信度与偏差

- 解析脚本独立于 `direction.py` 重写；出现级计数与它差 <0.1%（grep 32,050 vs 32,069，sed 15,236 vs 15,242）。
- token 归因是"首个实质命令"：一条调用含多个命令时，整条 token 记给第一个，所以"某个命令的 token"是调用级近似；多窗口 sed 调用里的 token 只记一次（第一处窗口），不重复计。
- 统计的是**模型实际看到的结果文本**（已截断 / 已 spill），所以数字反映真实上下文占用，而非命令原始输出量。
- 「可省量」分两类：第 1、4 项是可证的重复投递与实测行数；第 2、3 项是策略性截断的上界式估算（假设上下文窗口与整段读"用不到那么多"），落地前应按具体策略复测。
- 语料是活的：重跑会得到更大的快照，本文数字以 44,216 行的冻结快照为准。

## 附录：脚本与复现

中间数据落在 `OUT_DIR`（默认 `/tmp/dsh-bash-stats`），依赖报告已有的 `extract.py` / `extract_all.py` 产物：

```bash
export OUT_DIR=/tmp/dsh-bash-stats
cd docs/dsh-bash-usage
python3 extract.py        # 生成 OUT_DIR/rows（含结果文本）
python3 extract_all.py    # 生成 OUT_DIR/all_tools.jsonl（全工具，用于"之后改没改这个文件"）
python3 sedgrep_parse.py      # → OUT_DIR/sedgrep_parsed.jsonl
python3 sedgrep_purpose.py    # 形状 / 窗口 / 目标类型 / flag 组合 / 范围 / 管道 / 上下文占比
python3 sedgrep_optional.py   # 上下文封顶可省量、pattern 类型、目标扩展名
python3 sedgrep_redundancy.py # 重复读、grep→sed 链、同命令重复
python3 sedgrep_aftermath.py  # 每条 sed/grep 之后的动作、跨工具重复
python3 sedgrep_cost.py       # token 集中度、最贵调用样例、读回验证占比
python3 sedgrep_trim.py       # 每调用命令数、结果内重复行号、定位列表截断可省量
```

| 脚本 | 说明 |
|---|---|
| [`sedgrep_parse.py`](dsh-bash-usage/sedgrep_parse.py) | 复用 `classify.py` 的切分器，解析每条调用的 sed/grep 形状、窗口、目标、后续管道，并挂上结果文本 |
| [`sedgrep_purpose.py`](dsh-bash-usage/sedgrep_purpose.py) | 第一节：形状、窗口分布、目标类型、输出行数 vs 请求窗口 |
| [`sedgrep_optional.py`](dsh-bash-usage/sedgrep_optional.py) | `-A/-B/-C` 命中/上下文行数、封顶模拟、pattern 类型、目标扩展名 |
| [`sedgrep_redundancy.py`](dsh-bash-usage/sedgrep_redundancy.py) | 同会话同文件的重复/重叠读取、grep→sed 链（含链内命中行落在窗口外的比例） |
| [`sedgrep_aftermath.py`](dsh-bash-usage/sedgrep_aftermath.py) | 调用之后的动作分类（改 / 读 / 再读 / 无），含 cwd 解析与路径归一 |
| [`sedgrep_cost.py`](dsh-bash-usage/sedgrep_cost.py) | token 集中度、最贵调用样例、改前查阅 vs 改后验证 |
| [`sedgrep_trim.py`](dsh-bash-usage/sedgrep_trim.py) | 每调用命令数、结果内重复行号、定位列表截断到前 8 条的可省量 |

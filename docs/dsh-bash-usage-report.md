# 一、bash 命令频率与 token 占比

## 口径

- 按 `callId` 全局去重得 44,216 次 bash 调用；一次调用里通常有多个命令（79.3% 含 ≥2 个实质命令），分类按**首个实质命令**。
- `cd <dir> &&`（79.9% 的调用含）、纯变量赋值行（5.5%）、`echo "=== 标题 ==="` 段标记（48.4%）属样板，不计入分类。
- 结果 token 用 tiktoken `o200k_base` 近似计数，合计 **36,477,963 token / 98.3 MB** 文本。仅 11 次调用无结果文本。
- 「出现于调用中」= 该命令出现在调用任意位置的占比（含管道各段），所以 `| head` 这类会偏高。

## 几个结论

1. **调用次数高度集中**：grep + sed + git = 56.9% 的调用；再加 ls/cat 到前 5 类是 79.1%。grep 单独出现在 46.3% 的调用里。
2. **token 与次数严重不成比例**：git 只用 12.4% 的调用吃掉 25.1% 的 token（平均 1,666 tok/次，P90 4,882）。再拆一层，`git diff` 占 git 调用的 33%、却占 git token 的 **70.6%**（平均 3,380 tok/次）；`git show` 占 11.6% 调用 / 14.0% token。前 3 类占 70.5% token，前 5 类占 83.1%。
3. **grep 是「高频低产」的对照组**：28% 的调用只占 23.8% token（平均 698，P90 1,519）——输出普遍被 `-n`/`head` 收窄。真正吃 token 的是 `git diff`、`cat`（1,093）、`sed -n 大范围`（1,087）、`nl`（2,884）、heredoc `echo`（1,133）。
4. **纯等待几乎不产 token**：`sleep` 559 次调用平均 27 token；`pwd`/`rm`/`cp`/`tsc` 也在 200 上下。所以「减少 bash 调用次数」和「压缩 bash 输出」是两件不同的事。
5. **单次结果体积长尾很重**：p50 = 345、p75 = 834、p90 = 1,820、p99 = 8,070、max = 33,664 token；均值 825 被长尾拉高。
6. 长尾确实很长：`nl` 以下的 102 个类别合计只占 2.55% 调用 / 1.56% token。

## 可信度检查

- 主表数字在 **DSH-ClipClop 单项目**（35,129 次调用，占总量 79.4%）上复算基本一致：grep 29.3%/23.7%、sed 17.5%/22.2%、git 13.3%/26.5%——没有单个项目把结论带偏。反倒是 `deepseek-harness` 项目里 git 只占 3.1%、python 升到 12.2%（读源码为主，少 git diff）。
- 抽取逻辑用**另写的独立实现**在 v3、v4 各一个会话上对拍过：bash 调用数、配对结果数、结果文本字符数三项完全一致。
- 过程中修掉两个格式坑，值得记一笔：**v3 日志的 tool/result 没有顶层 `toolCallId`**（要读 `message.source.callId`），且**结果文本多嵌一层**（`[{type:'tool-result',content:[{type:'text',...}]}]`）。不处理这两点会漏掉 34% 的结果文本和约 1,240 万 token。

# 二、grep/sed/git 的读写分工

**结论：grep 对，sed 反了，git 不平衡。** 用同一批 44,216 次 bash 调用（218,508 个顶层简单命令）按读写意图分类后：

## 三者读写方向

| 命令 | 出现次数 | 读 | 写 | 判定 |
|---|---:|---:|---:|---|
| `grep` | 32,069 | 31,961（99.7%） | 108（0.3%） | ✅ 纯读 |
| `sed` | 15,242 | 15,037（98.7%） | 205（1.3%） | ❌ 几乎纯读，不是写 |
| `git` | 14,012 | 12,013（85.7%） | 1,925（13.7%） | ❌ 读远多于写 |

> ⚠️ 上表是当时的口径；其中 grep/sed 的「写」含少量误判，修正值见本节末尾「重定向误判修正」。

按**返回 token**（该命令作为首位实质命令的调用）看，偏斜更极端：

| 命令 | 结果 token 合计 | 读侧 | 写侧 |
|---|---:|---:|---:|
| `grep` | 8,671,381 | 8,651,198（99.8%） | 20,183（0.2%） |
| `sed` | 7,905,506 | 7,887,092（99.8%） | 18,414（0.2%） |
| `git` | 9,141,006 | 9,018,682（98.7%） | 109,924（1.2%） |

## sed 为什么是读

15,242 次 sed 里，**96.6% 是 `sed -n 'a,bp' file`（打印行区间）**，只有 0.9% 是 `-i` 原地写、0.4% 是重定向写：

| sed 形式 | 次数 | 占比 | token 占比 |
|---|---:|---:|---:|
| `-n 'a,bp'` 打印行区间（读） | 14,723 | 96.6% | 99.8% |
| 其他形式（只输出 stdout，读） | 328 | 2.2% | 0.0% |
| `-i` 原地写 | 133 | 0.9% | 0.2% |
| 重定向写文件 | 58 | 0.4% | 0.0% |

也就是说这里的 sed 不是「编辑器」，而是**比 `read` 工具更省的精确读取器**——只取文档里 15–30 行这种窄窗口。文件写入实际走的是别的路子：全语料写命令里 `awk > file` 924、`cp` 811、`cat > file <<EOF` 765、`rm` 764、`mkdir` 395、`python3 >` 273、`echo >>` 248，sed 只占 205 次。

## grep 的读也分三种

| grep 用法 | 次数 | 占比 | token 占比 |
|---|---:|---:|---:|
| 内容检索（`-n -A -B -o`） | 26,261 | 81.5% | 97.4% |
| `-v` 反选过滤（多在管道里） | 3,951 | 12.3% | – |
| 存在性/计数（`-l -c -q`） | 1,910 | 5.9% | 2.4% |
| 重定向写文件 | 108 | 0.3% | 0.2% |

注意有 18% 的 grep 其实不是「读数据」而是管道里的过滤/点名（`| grep -v node_modules`、`grep -q`），这部分不产生信息，只做筛选。

## git 是 86:14（次数）/ 98.7:1.2（token）

| 子命令 | 出现次数 | 占比 | 方向 | token（该命令为首位时） |
|---|---:|---:|---|---:|
| `git log` | 3,481 | 24.8% | 读 | 843,420 |
| `git diff` | 3,460 | 24.7% | 读 | **6,471,586** |
| `git status` | 2,545 | 18.2% | 读 | 278,292 |
| `git show` | 1,435 | 10.2% | 读 | 1,336,457 |
| `git add` | 859 | 6.1% | 写 | 81,318 |
| `git commit` | 852 | 6.1% | 写 | 10,061 |
| `git rev-parse` | 420 | 3.0% | 读 | 49,988 |
| `git ls-files` / `check-ignore` / `branch` | 198/137/81 | 3.0% | 读 | 19,417 |
| `checkout`/`tag`/`stash`/`clone` 等 | ~200 | 1.4% | 写 | ~18,900 |

读 12,013 次 vs 写 1,925 次。**`git diff` 一个子命令吃掉 git token 的 70.8%**，而所有写操作加起来只占 1.2%——因为 `add`/`commit` 几乎不输出内容。

> ⚠️ **更正**：早前一版 git 子命令表写的是 diff 1,748 次、commit 57 次。那份是「只数 git 作为首个命令的调用」，漏掉了 `git add -A && git commit` 这类串联（整条都归给了 `add`），而且 `git -C <路径> diff` 的全局参数解析有误。上表按**每个 git 简单命令出现一次**计数，并以正则独立复核过（1.4 万次量级、各子命令误差 <5%）。

## 整体口径

全语料 218,508 个顶层命令：读 45.7%、写 2.3%、git 6.4%、其他 45.6%（echo 44,239 和 cd 36,235 就占了其他的一大半，都是脚手架）。**整个 bash 使用是极度读密集的**——对「压缩 bash 输出 token」这件事的启示是：优化目标几乎全在读侧（diff/cat/sed 大范围/grep 全文件扫描），写侧没有可压的空间。

## 重定向误判修正

后续复查发现重定向检测把 `awk 'NR>=320 && NR<=400'` 这类**比较运算**误判成了 `> 文件`。修正后（详见[第三章的更正](#-更正上一轮的一个数字)）：

| 项 | 修正前 | 修正后 |
|---|---:|---:|
| grep 的「重定向写」 | 108 次 | **13 次** |
| grep 读 : 写 | 99.7% : 0.3% | **100.0% : 0.04%** |
| sed 的写 | 1.3%（205 次） | **1.0%（159 次：`-i` 133 + 重定向 16）** |
| sed 读 : 写 | 98.7% : 1.3% | **99.0% : 1.0%** |
| 全语料写类命令 | 5,011 次（2.3%） | **3,431 次（1.6%）** |

结论方向不变（bash 以读为主、sed 不是编辑器）。

# 三、DSH 写文件用什么工具/命令

## 结论：写文件的主力是 `edit` 工具，不是 bash

同一批去重后的全量调用（50,839 个 tool call，按 `callId` 去重）：

| 工具 | 调用次数 |
|---|---:|
| `bash` | 44,225 |
| `read` | 12,102 |
| **`edit`** | **5,530** |
| **`write`** | **819** |
| `read_image` | 269 |

`edit` 是 `write` 的 **6.8 倍**——DSH 基本不整文件重写，而是小步定点改。

## 写机制排名（次数，合计 12,000）

| 机制 | 次数 | 占比 |
|---|---:|---:|
| **`edit` 工具（定点替换）** | 5,530 | 46.1% |
| bash `git add` / `git commit` | 859 / 852 | 14.3% |
| bash `cp` / `mv`（复制移动） | 841 | 7.0% |
| **`write` 工具（整体新建/覆盖）** | 819 | 6.8% |
| bash `rm`（删除） | 766 | 6.4% |
| bash `cat > f <<EOF`（heredoc 造文件） | 764 | 6.4% |
| bash `mkdir` / `rmdir` | 400 | 3.3% |
| bash 重定向写（`printf`/`timeout`/`python3`/`pnpm`/`echo`/`sed … > f`） | 332 | 2.8% |
| bash `touch`/`chmod`/`ln` 等文件系统操作 | 157 | 1.3% |
| bash `sed -i`（原地改） | 133 | 1.1% |
| bash `python`/`node` 脚本里写文件 | 116 | 1.0% |
| bash `git checkout` / `git tag` 等其余版本库写 | ~134 | 1.1% |

读法：**bash 里的「写」大部分不是写内容，而是文件管理和版本库操作**（cp/mv/rm/mkdir/git 合计约 3,700 次）；真正在 bash 里生成文件内容的只有 heredoc 764 次 + 重定向 332 次 + 脚本内写 116 次，加起来约 1,200 次，只有 `edit` 工具的五分之一。

## 三者各自写了多少内容

| 载体 | 调用 | 写入字符 | 平均/次 | 唯一文件 |
|---|---:|---:|---:|---:|
| `write` 工具（content） | 819 | 3,956,293 | 4,831 | 637 |
| `edit` 工具（new_string） | 5,530 | 2,786,647 | 504（替换掉 267） | 481 |
| bash heredoc 正文 | 764 | 1,183,210 | ~1,550 | – |

分工很清楚：**`write` 负责大块内容落地（平均 4.8 KB/次），`edit` 负责高频小改（平均 504 字符/次）**。`edit` 的调用高度集中在少数文件上——被改最多的单个文件是 `chaser/mail/backend/SPEC.md`（182 次）和 `.scratch/dsh-navigator/issues/04-review-records-replay.md`（162 次）。

## 写到哪里

**扩展名**：`.md` 3,380（61%）、`.ts` 1,862、`.py` 449、`.tsx` 292、`.mjs` 122、`.json` 98 —— 写文件主要是**写文档/票据**，不是写代码。

**目录 top**（`write`+`edit`）：

- `.scratch/dsh-navigator/issues`（866 次 edit）、`.scratch/historical-reasoning-pruning/issues`（287）、`.scratch/dsh-result-clipper/*`（~510）
- `docs/`（493）
- `packages/dsh-result-clipper/src`（337+241）、`packages/dsh-result-clipper/tests`（291）、`packages/dsh-navigator/{src,tests}`（171+217）

**heredoc 的用途**很集中：`package.json`（24）、`tsconfig.json`（11）、`tests/*.spec.ts` 一堆探针、`probe.mjs`（6）——即**一次性脚手架和探针脚本**，用完就删，所以它不走 `write` 工具。

**失败率**：`edit` 224/5,530 = 4.1% 报错（基本是 `old_string` 没匹配上），`write` 19/819 = 2.3%。

## ⚠️ 更正上一轮的一个数字

早前说「bash 写命令只占 2.3%（5,011 次）」是**偏高**的：重定向检测把 `awk 'NR>=320 && NR<=400'` 这种比较运算误判成了 `> 文件`。修正后：

- 全语料写类命令：**5,011 → 3,431 次（1.6%）**
- grep 的「重定向写」：108 → **13 次**（即 grep 是 100% 读）
- sed 的写：1.3% → **1.0%**（`-i` 133 + 重定向 16）

结论方向不变（bash 以读为主、sed 不是编辑器），但上面这几个数字请用修正值。

# 附录 A：口径与可复现性

## 数据流

```
~/.dsh/sessions/**/session*.jsonl.zstd
   │  extract.py          zstd 解压 + 配对 tool/call 与 tool/result（兼容 v3/v4 两种结构）
   ▼  rows/*.jsonl         每会话一个中间文件
   │  classify.py         按 callId 全局去重 + 首个实质命令归类
   ▼  calls.jsonl          44,216 行
   │  final.py            tiktoken 计数
   ▼  tokens.json / stats.json
   │  report.py           第一章的分组表（含分项目交叉验证）
   │  direction.py        第二章的读写方向表
   │  export_csv.py       bash-calls-classification.csv
   │
   │  extract_all.py      另一条支线：全部工具（bash/read/edit/write/read_image）
   ▼  all_tools.jsonl      50,839 个去重 tool call
      writers.py          第三章的写机制表
```

## 复现命令

```bash
export OUT_DIR=/tmp/dsh-bash-stats
python3 extract.py        # ~26s
python3 classify.py       # ~4s
python3 final.py          # ~6s
python3 report.py         # 第一章的分组表
python3 direction.py      # 第二章的读写方向表
python3 export_csv.py     # 明细 CSV
python3 extract_all.py    # ~25s，全工具
python3 writers.py        # 第三章的写机制表
```

脚本默认 `OUT_DIR=/tmp/dsh-bash-stats`，可用环境变量覆盖。全部依赖标准库 + `zstd` 命令行 + `tiktoken`。

## 已知偏差

| 偏差 | 说明 |
|---|---|
| 语料持续增长 | 会话日志随当前会话写入，重跑行数会变（写作期间 44,216 → 44,238，占比漂移 ≤0.05 个百分点） |
| 两条支线行数差 9 行 | `calls.jsonl`（44,216）与 `all_tools.jsonl` 的 bash 子集（44,225）去重时文件遍历顺序不同，同一 callId 有多个副本且内容不一致时保留哪一份不同。占比无影响 |
| token 非真实分词 | 用 `o200k_base` 近似 DeepSeek 的分词，绝对 token 数会有系统误差；本文结论全部基于**同类之间的相对占比**，不受影响 |
| 结果文本已被 DSH 处理 | 记录的 `tool/result` 是模型实际收到的内容（已截断/摘要/落盘），统计反映的是真实上下文占用，而非命令原始输出量 |
| python/node 内部读写 | heredoc 里的脚本是在读还是在写无法从命令行判定，统一归入「其他」；抽样含写文件迹象的只占 2% |
| 分类粒度是「首个实质命令」 | 一次调用含多个命令时，整条调用的结果 token 归给首个实质命令，因此「token 占比」是按调用归属而非按命令精确切分 |

## CSV 列

| 列 | 含义 |
|---|---|
| `call_id` | 工具调用 id（去重键） |
| `session_id` | 会话 id |
| `project` | 会话工作目录的 basename |
| `log_format` | 日志格式版本（v3/v4） |
| `primary_category` | 首个实质命令（本文表格的「类别」） |
| `commands_in_call` | 该调用里出现过的全部实质命令（去重，`\|` 分隔） |
| `simple_command_count` | 顶层简单命令个数 |
| `result_tokens` | 结果文本的 `o200k_base` token 数 |
| `result_chars` | 结果文本字符数 |
| `is_error` | 工具结果是否标记为错误 |
| `command` | 原始 bash 命令全文 |

> CSV 按 RFC 4180 引号转义，`command` 列保留多行命令的换行，因此 `wc -l` 会显示约 15.4 万物理行；按 CSV 解析后是 **44,216 条记录**（表头另计）。校验方式：`primary_category` 分组计数与 `result_tokens` 求和必须与[第一章主表](#全部-dsh-历史)一致（grep 12,416 / sed 7,273 / git 5,486 …，token 合计 36,477,963）。

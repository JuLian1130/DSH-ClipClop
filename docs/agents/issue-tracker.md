# Issue Tracker: Local Markdown

本仓库的规格和任务保存在 `.scratch/`。

## Conventions

- 每个功能使用一个目录：`.scratch/<feature-slug>/`。
- 功能规格保存为 `.scratch/<feature-slug>/spec.md`。
- 规格顶部使用 `Status:` 记录状态；可交由编码代理实施的规格使用 `ready-for-agent`。
- 拆分实施任务的票在 `.scratch/<feature-slug>/issues/` 下按 `01-<slug>.md` 顺序创建：一张票一个文件，编号按依赖顺序（阻塞者在前），每票的 Blocked by 写明它依赖的票。

当技能要求发布到 issue tracker 时，按以上约定创建或更新对应 Markdown 文件。

## 复审与收敛

票面写判据，机制写在 `docs/<feature>-design.md`：复审只该在票里找**判据层**（验收项是否可观察、是否引到规格出处、层级是否放错、前置是否漏）与**机制断言层**（票面新引入的机制结论是否有误、是否与源码或现状冲突）两类问题；措辞、编号、出处、记账这类只影响可读性的项按低严重度处理，不单独开一轮。

- 一轮复审**算收敛**，当且仅当它没有判据层发现、也没有机制断言层发现。只剩低严重度项时不再补一轮解释，而是把「已决定不改」的条目连同理由写进票面，供下一轮直接跳过。
- 连续两轮的发现集中在同一段落，说明问题不在措辞而在结构：改写票面（把机制移进设计文档、把说明降级为缩进段、合并过碎的勾选项），而不是再补一轮解释。
- 机制描述只留一处。票面只写判据 + 规格出处 + 观察面（加上「形状即决定」时才内联的形状）；DSH 机制、源码依据、实测与源码核对的分界都写进设计文档的机制节与「验证状态」，票面用章节名指过去。

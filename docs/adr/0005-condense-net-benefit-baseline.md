# 工具结果精简的净收益闸门以模型本来会看到的量为基准

状态：接受（2026-10-16 确认）。

精简层在决定是否替换正文之前，把「精简后的总成本（含回退入口说明的开销）」与**模型本来会看到的正文**比较，而不是与工具产出的原文比较；前者不严格更小就交回后者。闸门不可配置关闭。这里的「模型本来会看到的正文」指下游处理完成之后的投影——即 spill 策略与其他 `tools/post-execute` 监听器都已经跑过的那一份，也是隐私判断与摘要候选测量的同一份。

参照实现的字面口径是对原文比较（调研 §5.1 #2 转引的 `guard.rs` / `validate.rs`，以及 RTK 的后置路径）。本仓偏离它的理由是 DSH 与那些实装的层序不同：spill 策略会先按 token 预算把过大结果压到头尾各留一半，本仓 base bundle 的预算是 12,500 token。实测语料印证了这一点——`bash` 与 `web_fetch` 的结果正文正好封顶在 50,000 字符（= 6,250 + 6,250 token 的两半预算），而 `read` 被 spill 硬编码豁免，最大 57,507 字符、不受该顶。以原文为基准会让一条已被压到 5 KB 的结果被替换成 40 KB 的精简结果，上下文占用反而增加，与这一层「节省进入上下文的 token」的目标直接冲突。

这是真取舍，在「多 token 换更多信息」与「绝不增加 token」之间选了后者。代价是闸门在 spill 命中时收得更紧，省幅读数比「对原文」口径小；而在 spill 根本不介入的那一段（实测 bash 的 token 里约 92% 未被 spill 触碰），基准就等于原文，本层可以自由发挥。另一条有意保留的推论：精简后的正文同时是摘要候选的测量基准，所以精简若把某条结果压到摘要下限以下，主模型在调用参数里声明的取回目标就不会被满足——那是有意为之，不当缺陷修，出口是模型声明整份或逐字。
